# 视频全量转文本与向量化记忆设计方案

## 1. 背景与目标

### 1.1 现状问题

当前 `video_parser.py` 对视频的解析只做了一半：

| 信息通道 | 承载内容 | 当前状态 |
|----------|----------|----------|
| 🎧 音频轨 | 语音讲解、旁白 | ✅ 已实现：ffmpeg 提取音频 → Whisper 转写进 `raw_text` |
| 🖥️ 画面轨 | PPT、字幕、板书、演示画面 | ❌ 仅抽帧出路径（`images`），**文本语义丢失**，VLM 描述被推迟到 Rust 端 |

问题：

- 视频中的 **PPT/字幕/关键图表** 信息没有被提取成文本，导致知识库检索时无法命中这些内容；
- 视频文本未**切片向量化**，无法支持"一次上传、永久记忆、随问随答"的 RAG 体验；
- 重复上传同一视频会重复解析（浪费算力），没有记忆去重机制。

### 1.2 目标

1. **全量文本化**：将视频的语音 + 画面（OCR）全部转为带时间戳的文本；
2. **一次上传永久记忆**：文本切片 → 向量化 → 持久化到向量库；同一视频重复上传自动幂等跳过；
3. **RAG 问答**：问答时从向量库检索相关切片（可回指视频时间点），拼接 Prompt 交给 LLM/VLM 生成回答；
4. **与既有设计对齐**：复用 `docs/文档解析后向量化数据缓存方案.md` 的 LanceDB 主存储 + pgvector 归档架构，保证 Rust 后端与 Python 侧车维度一致、数据互通。

## 3. 视频全量文本化（VideoParser 增强）

### 3.1 现有代码结构

`apps/doc-parser/parsers/video_parser.py`（现有能力）：

```python
async def parse(self, file_path: str, options: dict = None) -> ParseResult:
    # 1. ffmpeg.probe 获取元数据（时长/分辨率/音轨）
    # 2. 提取音频 → AudioParser(Whisper) 转写 → raw_text
    # 3. 定时抽帧（每 30s 一帧；>30 分钟只取首尾 5 分钟）→ frame_paths
    # 返回 ParseResult(file_type="video", raw_text, images=frame_paths, metadata)
```

### 3.2 增强设计

在抽帧循环内，对每帧调用 `utils/ocr.py` 现有 `ocr_image_path()`：

```python
# 伪代码：通道2 帧 OCR
for t in timestamps:
    frame_path = os.path.join(tmpdir, f"frame_{t:06d}.jpg")
    ffmpeg.input(file_path, ss=t).output(frame_path, vframes=1).run(...)
    ocr_text = ocr_image_path(frame_path, lang="chi_sim+eng")
    if ocr_text.strip():
        frame_texts.append({"time_sec": t, "type": "ocr", "text": ocr_text.strip()})
```

**混合文本输出格式**（含时间戳，便于后续切片与回溯）：

```
[00:00-00:30 语音] 工业机器人控制软件可以认为是由两大部分组成...
[00:00-00:30 画面] 机器人硬件系统组成图：控制系统、示教器、机器人本体...
[00:30-01:00 语音] 实时部分负责运动学算法的调度和规划...
[00:30-01:00 画面] 实时系统组成：伺服驱动器、板卡、芯片...
```

### 3.3 输出结构调整

| 字段 | 现在 | 增强后 |
|------|------|--------|
| `raw_text` | 仅语音转写 | 语音 + 画面 OCR 混合文本（带时间戳） |
| `images` | 帧路径列表 | 不变（供 Rust VLM 逐帧解读，两者可并行） |
| `metadata["frames_extracted"]` | 帧数 | 不变 |
| `metadata["ocr_frames"]` | 无 | **新增**：有 OCR 文本的帧数 |
| `metadata["segments"]` | 无 | **新增**：带时间戳的文本段列表 `[{time, type, text}]` |

### 3.4 抽帧策略增强（可选）

现策略：固定 30s 一帧，>30 分钟只取首尾。全量转文本建议增加：

- **场景变化检测**：`ffmpeg -vf "select='gt(scene,0.3)'"` 按场景切换抽帧（PPT 翻页即抽），避免长镜头冗余、快闪漏检；
- **OCR 质量阈值**：连续多帧 OCR 内容高度相似（如 >0.9 重复率）时跳过，减少入库冗余；
- 保留现有 `FRAME_INTERVAL_SEC` 配置兜底。

## 4. 文本切片方案（TextChunker）

### 4.1 切片策略

| 策略 | 说明 | 适用 |
|------|------|------|
| **时间窗口** | 按固定窗口（默认 30s/60s）切分，与 `FRAME_INTERVAL_SEC` 对齐 | 讲座、课程类长视频 |
| **字符数** | 按 ~500 字/片切分（中文），避免超长切片稀释语义 | 通用兜底 |
| **语义边界** | 结合 Whisper `segments` 断句 + 换行/标题，尽量在句末切开 | 精度优先 |

**建议**：先按时间窗口切（简单、时间可回溯），文本超长再按字符数二次切分。

### 4.2 切片数据结构

```python
@dataclass
class VideoChunk:
    video_id: str            # 视频唯一 ID（文件 SHA-256 或业务 ID）
    chunk_index: int         # 切片序号
    start_sec: int           # 起始时间（秒）
    end_sec: int             # 结束时间（秒）
    type: str                # voice / ocr / mixed
    text: str                # 切片文本（含时间戳前缀）
    file_name: str           # 原视频文件名（溯源）
    created_at: str          # 创建时间（ISO8601）
```

## 5. 向量化与存储（记忆）

### 5.1 Embedding 模型选型

与 `docs/文档解析后向量化数据缓存方案.md` 保持一致（**维度必须与 Rust 端 LanceDB 一致**）：

| 模型 | 维度 | 说明 |
|------|------|------|
| `BAAI/bge-small-zh-v1.5` | 512 | 轻量、快，中文推荐（默认） |
| `BAAI/bge-base-zh-v1.5` | 768 | 精度更高，与 Rust 端 `vector(768)` 对齐 |

> 依赖 `sentence-transformers`（已有），首次使用会下载模型。

### 5.2 LanceDB 主存储

**数据目录**：`{data_dir}/lancedb/`（与 Rust 端同路径约定，保证可以共用）

**表名**：`video_knowledge`

**表结构**（在 Rust 端 `asset_knowledge` 基础上扩展视频定位字段）：

```python
import lancedb
import pyarrow as pa

schema = pa.schema([
    pa.field("id", pa.string()),                    # 主键（video_id + chunk_index）
    pa.field("video_id", pa.string()),              # 视频唯一 ID
    pa.field("vector", pa.list_(pa.float32(), 768)),# 向量（维度与 Embedding 一致）
    pa.field("chunk_index", pa.int32()),
    pa.field("start_sec", pa.float32()),            # 视频内起始秒
    pa.field("end_sec", pa.float32()),              # 视频内结束秒
    pa.field("type", pa.string()),                  # voice / ocr / mixed
    pa.field("content", pa.string()),               # 切片完整文本
    pa.field("file_name", pa.string()),             # 原视频文件名
    pa.field("permission_level", pa.string()),      # 权限等级
    pa.field("doc_source", pa.string()),            # 来源（video:xxx）
    pa.field("deleted", pa.int16()),                # 软删除标志
    pa.field("created_at", pa.timestamp('us')),
])
```

**索引**：参照 Rust 端创建 IVF-PQ：

```python
table.create_index(metric="cosine", num_partitions=256, num_sub_vectors=96)
```

### 5.3 幂等去重（记忆的关键）

```python
import hashlib

def video_sha256(file_path: str) -> str:
    h = hashlib.sha256()
    with open(file_path, "rb") as f:
        for block in iter(lambda: f.read(1 << 20), b""):
            h.update(block)
    return h.hexdigest()
```

入库前：
1. 计算文件 SHA-256 → `video_id`；
2. 查询 LanceDB：`video_id` 且 `deleted=0` 的记录是否存在；
3. **存在 → 直接返回已入库状态，跳过解析**（无需再次 Whisper/OCR/Embedding）。

### 5.4 pgvector 归档（可选）

沿用 Rust 端设计：LanceDB 写入后异步归档到 PostgreSQL `asset_knowledge`，作为备份与跨节点共享。桌面版可暂不启用。

## 6. RAG 检索与问答（通道3）

### 6.1 检索流程

```
用户问题（文本）
  → ① Embedding（同一模型）→ 查询向量
  → ② LanceDB.search(query_vector, top_k=10)
  → ③ 结果过滤 deleted=0 + 权限过滤
  → ④ 返回切片列表（含 start_sec/end_sec、相似度 score）
```

### 6.2 回答生成（LLM/VLM）

```
拼接 Prompt：
  [系统] 你是知识库助手。基于以下视频内容切片回答问题，并注明内容所在的视频时间点。
  [上下文]
  [01:00-01:30 语音] ...
  [01:00-01:30 画面] ...
  [问题] ...
  → LLM/VLM 生成回答（引用时间：12:30-14:00 的内容...）
```

### 6.3 时间回溯价值

每个切片保留 `start_sec/end_sec`，回答可定位到 **"这段内容出现在视频 12:30-14:00"**，用户也能据此直接跳转视频对应位置，形成"文本问答 ↔ 视频播放"闭环。

## 7. 记忆生命周期

| 操作 | 行为 |
|------|------|
| **新增（首次上传）** | 解析 → 切片 → Embedding → 写入 LanceDB（落盘） |
| **查询（问答）** | 问题 Embedding → 向量检索 → LLM 生成回答 |
| **重复上传** | SHA-256 命中 → 跳过解析，直接复用已有记忆 |
| **删除视频** | 按 `video_id` 软删除（`deleted=1`），LanceDB + pgvector 同步 |
| **更新视频** | 重新解析，`merge_insert` 替换该 `video_id` 的切片 |

## 11. 注意事项

1. **向量维度一致性**：Python 侧 Embedding 维度必须与 Rust 端 LanceDB/pgvector 一致（512 或 768），否则跨端检索出错；
2. **OCR 语言**：`chi_sim+eng` 已默认，英文/日文视频需对应调整（`OCR_LANGUAGE`）；
3. **Whisper 同音错字**：转写文本存在同音错字（如"试骂器/试试器"），可后续加一遍 LLM 纠错；
4. **抽帧覆盖**：`>30 分钟只取首尾` 的策略在全量转文本场景下应改用场景检测抽帧，避免中间内容丢失；
5. **权限过滤**：所有检索必须带 `permission_level` 过滤（多租户）；
6. **软删除同步**：LanceDB 软删除后需同步清理 pgvector 归档与（Rust 端）内存缓存；
7. **成本**：首次解析 + Embedding 为一次性开销，重复问答只做检索 + LLM 生成，成本可控。
