## 0. 文档定位与能力边界

### 0.1 三块能力与归属（关键决策）

| 能力 | API（Docker / K8s） | 归属 crate | 是否起进程 | 归属版本 |
|---|---|---|---|---|
| 容器日志 | `GET /containers/{id}/logs` / `GET .../pods/{pod}/log` | `ops`（只读） | 否，daemon / kubelet 读日志 | V1.1 |
| 容器性能 | `GET /containers/{id}/stats` / `GET /apis/metrics.k8s.io/v1beta1/.../pods/{pod}` | `ops`（只读） | 否，读 cgroup / metrics-server | V1.1 |
| 容器终端 | `POST /containers/{id}/exec` → `/exec/{id}/start` → `/exec/{id}/resize` / `POST .../pods/{pod}/exec`（WebSocket） | **新 crate `ops-exec`**（docker + k8s 两个 backend） | **是**，在容器内起 shell | V1.2 |

> K8s 的「性能」没有 Docker `stats` 那种逐容器实时接口：只能用 metrics-server 的 CPU / 内存快照
> （默认 15s 聚合窗口），**不承诺**网络 / 磁盘 / pids（见 §1.5、§6.8）。

分家的理由：`ops` 的只读纪律写在三处（`crates/ops/README.md`、`crates/ops/src/lib.rs` 文档头、采集方案 §6），
日志/性能是 GET 语义，可以进；exec 是“在目标容器里执行任意命令”，属总方案 §5 的写操作范畴，
必须独立 crate + 独立权限点 + 独立审计，避免被顺手挂进只读采集链路。

> 补充事实：这两类“进不去容器也能看”的能力，恰好覆盖 `scratch` / distroless 镜像 —— 见 §1.3。

### 0.2 不做什么

| 不做 | 归属 |
|---|---|
| 原始日志 / 指标落库 | 总方案 §4.2「原始日志不入库」，本方案只做内存拼装 + 前端展示 |
| 日志脱敏规则与 AI 故障总结 | 总方案 §4.3 / §4.4，独立任务（本方案只留调用点） |
| 启停 / 删除 / 改配置 | 总方案 §5，V1.2 |
| 容器内 SSHD | 总方案 §6.2 明确禁止，终端一律走 exec 内核命名空间接入 |
| 远程 Docker 的终端打通验证 | 本轮只验收本机 socket 与 mTLS 端点，2375 明文端点默认拒绝 exec |
| `docker attach` 语义 | 它接 PID 1 的 stdio，误按 `Ctrl+C` 会带走主进程；不提供 |
| 接 Prometheus / 读 kubelet Summary | 前者属独立监控栈；后者需 `nodes/proxy`（高危），本轮明确不做（§1.5） |

### 0.3 验收口径（DoD）

- 后端：**6 个 service 入口 + 6 条受保护 HTTP 路由 + 6 个 Tauri 命令**（Docker 日志/指标、K8s 日志/指标、终端开/关），
  命名逐字对齐；另有 **1 条 WS 通道**（票据鉴权，无对应 Tauri 命令）。
- 日志：Docker 侧对 `scratch` 容器的日志可读、`tail` 生效、超字节上限返回 `truncated=true`；
  K8s 侧能按 `namespace/pod[/container]` 流式读取，`previous=true` 可取崩溃前日志。
- 性能：Docker 侧 `one_shot` 与「两样本」两种模式都可返回，CPU% / 内存工作集 / 网络累计有单测；
  K8s 侧能读 metrics-server 的 CPU / 内存，**未安装时给出可读降级提示**而不是 500。
- 终端：Docker 与 K8s 都能打开 xterm 并完成 `ls`、`resize`、`exit` 全流程；无 shell 的镜像返回中文错误
  「该镜像不含 shell（scratch/distroless），请改用日志/性能或 debug sidecar」，而不是裸 500。
- 安全：exec 默认关闭；权限点 `ops:terminal:exec` 缺失时接口 403；审计行只含元数据。
- 验证：`cargo test -p ops --features docker,k8s`、`cargo test -p ops-exec`、`cargo check -p service -p api`、
  `pnpm --filter web test` 全绿。

## 1. 现状核查（实施前必须知道的五条硬事实）

### 1.1 `ops` crate 目前只有 health / collect

`crates/ops/src/connector/docker.rs` 的 `impl Connector for DockerConnector`（L417 起）只实现 `health()` / `collect()`，
内部只调用 `ping` / `version` / `info` / `list_containers` / `list_images` / `list_networks` / `list_volumes` /
`list_nodes` / `list_services` / `list_tasks`。全仓 **没有** `logs` / `stats` / `create_exec` 的调用。

结论：本方案是**新增能力**，不是“打开开关”；现有 `collect` 的行为、`asset_ops_link` 的写入口径都不变。

### 1.2 bollard 0.21.1 的 API 事实（逐条标注源码位置）

> 下表全部核对自 `~/.cargo/registry/src/*/bollard-0.21.1` 与 `bollard-stubs-1.53.1-rc.29.3.1`，不是文档猜测。

| 能力 | 签名 | 源码位置 | 关键约束 |
|---|---|---|---|
| 日志 | `logs(name, Option<LogsOptions>) -> impl Stream<Item = Result<LogOutput, Error>>` | `container.rs:928` | 默认 `stdout=false` / `stderr=false`，**必须显式打开**，否则空流 |
| 性能 | `stats(name, Option<StatsOptions>) -> impl Stream<Item = Result<ContainerStatsResponse, Error>>` | `container.rs:1014` | `StatsOptions` 默认 `stream=true`，不显式关掉流不结束 |
| 建 exec | `create_exec(container, impl Into<ExecConfig>) -> CreateExecResults` | `exec.rs:172` | 只登记，不校验二进制是否存在 |
| 启 exec | `start_exec(exec_id, Option<StartExecOptions>) -> StartExecResults` | `exec.rs:225` | `detach=false` 时走 HTTP Upgrade，返回 `Attached { output, input }` |
| 查 exec | `inspect_exec(exec_id) -> ExecInspectResponse` | `exec.rs:315` | 取 `running` / `exit_code`（127 = 命令不存在） |
| 改窗口 | `resize_exec(exec_id, impl Into<query_parameters::ResizeExecOptions>) -> ()` | `exec.rs:362` | **仅 `tty=true` 时有效** |

关键类型：

```rust
// container.rs:96 —— 日志帧已由 bollard 解复用（read.rs:32 NewlineLogOutputDecoder）
pub enum LogOutput {
    StdOut { message: Bytes },
    StdErr { message: Bytes },
    StdIn  { message: Bytes },
    Console { message: Bytes },   // TTY 容器 / exec tty=true：无帧头，按行或整块
}

// exec.rs:99
pub enum StartExecResults {
    Attached {
        output: Pin<Box<dyn Stream<Item = Result<LogOutput, Error>> + Send>>,
        input:  Pin<Box<dyn AsyncWrite + Send>>,
    },
    Detached,
}

// exec.rs:86-95
pub struct StartExecOptions {
    pub detach: bool,
    pub tty: bool,
    pub output_capacity: Option<usize>,   // 默认 8 KiB，终端场景建议 16~64 KiB
}
```

三个必须记住的坑：

1. **`LogsOptions` 没有 `previous` 字段**（字段只有 `follow/stdout/stderr/since/until/timestamps/tail`）。
   `docker logs --previous` 的能力在当前 bollard 版本**不可用**，与总方案 §4「崩溃容器 previous=true」存在差距 ——
   要补只能自建原始 HTTP 请求，或把 bollard 升级到生成该参数的版本（见 §9 风险 1）。
2. **`StatsOptions` 默认 `stream=true`、`one_shot=false`**。不写 `.stream(false).one_shot(true)` 就得到一个永不结束的流，
   HTTP 连接常驻，桌面端会表现为“性能页一直转圈、连接数上涨”。
3. **`tty=true` 时输出是 `LogOutput::Console`**（`exec.rs:270` 用 `NewlineLogOutputDecoder::new(true)`，
   `read.rs:50-69` 对 TCP 分支直接把整块当 `Console`），没有 8 字节帧头，stdout/stderr 也已被合并 ——
   终端就是要这个形态，**不要**再按 `StdOut`/`StdErr` 去 demux。

### 1.3 `scratch` 镜像没有 shell（为什么本仓的 otel-collector 进不去）

`docker-compose.yml` 里的 `otel-collector` 用的是官方 `otel/opentelemetry-collector-contrib:latest`，
其 Dockerfile 最终阶段是 `FROM scratch`：

```dockerfile
FROM alpine:3.24 AS certs
RUN apk --update add 'ca-certificates>=20261020-r0'
FROM scratch                      # ← 最终镜像，只有 /otelcol-contrib
ENV USER_UID=10001 USER_GID=10001
USER ${USER_UID}:${USER_GID}
COPY --from=certs /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/ca-certificates.crt
COPY --chmod=755 otelcol-contrib /otelcol-contrib
ENTRYPOINT ["/otelcol-contrib"]
```

⇒ 容器内没有 `sh` / `bash` / `ls` / `cat`，`docker exec -it otel-collector sh` 报
`exec: "sh": executable file not found in $PATH`。**bollard 同样无能为力**（不是 API 权限问题，是镜像里真没有这个文件）。

但这不影响本方案的两块只读能力：日志与性能都是 **daemon 侧**取数（日志驱动 + cgroup），不进入容器用户态。
`docker.top_processes()`（等价 `docker top`）同样可用，可作为“看进程”的轻量替代。

### 1.4 可复用的既有基础设施（决定终端怎么实现）

终端链路不新造轮子，直接复用 SSH 终端已经跑通的三件套：

| 组件 | 位置 | 可复用点 |
|---|---|---|
| 一次性票据 | `crates/api/src/ssh_ticket.rs` | `uuid v4`、单次消费、绑定 `session_id`、默认 60s、`SSH_TICKET_TTL_SECS` 可覆盖 |
| WS 双工泵 | `crates/api/src/ssh_routes.rs:357`（`session_ws`）/ L398（`pump`） | **Binary 帧 = 数据**，**Text 帧 = `{type:'resize'|'ping'|'close'}` 控制**；客户端发非 JSON 文本时按原始输入处理 |
| 前端终端 | `apps/web/src/hooks/useSshTerminal.ts` + `components/Ops/SshTerminalPanel.tsx` | xterm 动态导入、`FitAddon`、120ms 防抖 resize、卸载时 `closeXxxSession` 兜底 |
| 会话审计 | `crates/service/src/ssh_service.rs`（`insert_session_row` L720 / `finalize_session_row` L745） | 表结构与“opening → active → closed/failed”状态机可直接照抄 |
| 配额与回收 | `ssh_service.rs` L40 `DEFAULT_MAX_SESSIONS_PER_USER = 3`、L42 `DEFAULT_IDLE_SECS = 1800`、L1111 `spawn_idle_reaper()` | 常量、环境变量口径、空闲回收任务同构 |

> 结论：终端的工程量主要在“bollard exec 会话管理 + 审计落库 + 前端面板”，**WS 协议层基本零新增设计**。

### 1.5 K8s 侧事实核查（kube-rs 5.1.0）

> 与 §1.2 同口径：下表全部核对自本机 cargo registry 的 `kube-client-5.1.0` / `kube-core-5.1.0` / `k8s-openapi-0.29.0`。

| 能力 | API | 源码位置 | 关键约束 |
|---|---|---|---|
| 日志（全量） | `Api::<Pod>::logs(name, &LogParams) -> Result<String>` | `kube-client/src/api/subresource.rs:568` | 一次性收完，适合 ≤2000 行 |
| 日志（流式） | `Api::<Pod>::log_stream(name, &LogParams) -> impl AsyncBufRead` | 同上 `:599` | 按行读 + 字节上限，**本方案采用** |
| 日志参数 | `LogParams { container, follow, limit_bytes, pretty, previous, since_seconds, since_time, tail_lines, timestamps }` | `kube-core/src/subresource.rs:17-43` | `since_time` 是 `jiff::Timestamp`；用 `since_seconds` 避免引入 jiff |
| 建终端 | `Api::<Pod>::exec(name, command, &AttachParams) -> AttachedProcess` | `kube-client/src/api/subresource.rs:726` | **`#[cfg(feature = "ws")]` 门控** |
| 终端参数 | `AttachParams { container, stdin, stdout, stderr, tty, max_*_buf_size }` + `interactive_tty()` / `.container()` | `kube-core/src/subresource.rs:143-245` | `interactive_tty()` = stdin/stdout on、**stderr off**、tty on（TTY 下不能开 stderr） |
| 进程句柄 | `AttachedProcess::{stdin, stdout, stderr, terminal_size, join, take_status}` | `kube-client/src/api/remote_command.rs:189/209/229/286/245/266` | 尺寸 `TerminalSize{width,height}`（`:34`） |
| 指标 API | `ApiResource::from_gvk_with_plural(&GroupVersionKind::gvk("metrics.k8s.io","v1beta1","PodMetrics"), "pods")` + `Api::<DynamicObject>::namespaced_with` | `kube-core/src/discovery/mod.rs:39`、`kube-client/src/api/mod.rs:113` | `DynamicObject.data: serde_json::Value`（`kube-core/src/dynamic.rs:36`） |

K8s 侧的三个坑（与 Docker 的三个坑同等重要）：

1. **`exec` 需要 kube 的 `ws` feature**：`kube-client/Cargo.toml:140` 定义
   `ws = ["client", "tokio-tungstenite", "kube-core/ws", "tokio/macros"]`。当前根 `Cargo.toml` 的 kube 是
   `default-features = false` + `client/config/rustls-tls/ring`，**没有 `ws`** —— 不开就编译不过；开了会拉入
   `tokio-tungstenite`，桌面端编译时间与包体积都会上涨（这是终端放独立 crate 的直接理由）。
2. **`ApiResource::from_gvk` 会算错 plural**：它内部 `to_plural("podmetrics")` 得到 `podmetrics`，而 metrics API
   的资源名是 **`pods`**（`kind=PodMetrics`）。必须用 `from_gvk_with_plural(..., "pods")`，否则请求打到
   `/apis/metrics.k8s.io/v1beta1/namespaces/{ns}/podmetrics` → 404。
3. **`AttachedProcess::join()` 必须在读干 stdout/stderr 之后调用**：kube 源码注释（`remote_command.rs:245-250`）
   写明——否则内部 simplex 缓冲写满、后台任务阻塞、`join` 永不返回（死锁）。

指标能力边界（已确认，非实现取舍）：

- `k8s-openapi 0.29` **不含** `metrics.k8s.io` 类型（全库 grep 零命中），只能用 `DynamicObject` 走 JSON；
- metrics-server 只提供 **CPU（nanocores 字符串，如 `"12345678n"`）与内存（`"12345Ki"`）**，Pod + 容器级，窗口默认 15s；
- **没有** 网络 / 块设备 / pids / 重启计数（这些仍可从 `pods` 对象与 `ops` 采集快照里拿，但不是实时值）；
- 未安装 metrics-server 或账号无权限时，APIServer 对 `metrics.k8s.io` 返回 404/403，必须映射为可读文案（§6.8）。

与 Docker 的差异（决定「不能照抄」的地方）：

| 维度 | Docker（bollard） | K8s（kube-rs） |
|---|---|---|
| 日志定位 | 容器 ID / 名 | namespace + pod + container（多容器 Pod 必须显式指定） |
| 崩溃前日志 | ❌ 0.21.1 无 `previous` | ✅ `LogParams.previous = true`（覆盖 CrashLoopBackOff） |
| 日志字节上限 | 应用层累加截断 | ✅ 原生 `limit_bytes`，再加 `tail_lines` |
| 性能字段 | CPU / 内存 / 网络 / 块设备 / pids | 仅 CPU / 内存（metrics-server） |
| 性能时延 | 1s 一个样本，近实时 | 15s 聚合窗口，非实时 |
| 终端协议 | HTTP Upgrade + 单流 | WebSocket + 多信道（0 stdin / 1 stdout / 2 stderr / 3 status / 4 resize） |
| 退出码 | `inspect_exec().exit_code` | `take_status()` 的 `Status.details.causes[reason=ExitCode]` |

## 2. 数据模型

### 2.1 日志与性能：零新表

- 日志与指标都**按需拉取、内存拼装、随响应返回**，不落库（对齐总方案 §4.2）。
- 不写 `asset_ops_link`、不改 `assets`、不新增“指标表”；采集口径与写入口径完全不变。
- 若将来要做趋势图，再单独评估时序存储（PG 分区表或外部 TSDB），不在本方案范围。

### 2.2 `ops_terminal_session`（仅终端会话审计，Docker + K8s 共用）

只有终端需要审计行。结构对齐既有 `ops_ssh_session`（`id / target_id / user_id / state / client_ip /
started_at / ended_at / bytes_in / bytes_out / exit_code / error`），把 `target_id` 换成「连接 + 目标」，
并用 `provider` / `target_kind` 区分 Docker 容器与 K8s Pod：

```sql
CREATE TABLE IF NOT EXISTS {schema}.ops_terminal_session (
    id             BIGINT PRIMARY KEY,
    provider       VARCHAR(16) NOT NULL,     -- docker / k8s
    connection_id  BIGINT NOT NULL,          -- ops_connection.id
    target_kind    VARCHAR(16) NOT NULL,     -- docker_container / k8s_pod
    container_uid  VARCHAR(255),             -- Docker：容器 Id（asset_ops_link.resource_uid）
    namespace      VARCHAR(255),             -- K8s 命名空间
    pod_name       VARCHAR(255),             -- K8s Pod 名
    container_name VARCHAR(255),             -- 两边都有（K8s 多容器必填）
    shell          VARCHAR(64),              -- /bin/sh / /bin/bash ...
    user_id        BIGINT NOT NULL,
    state          VARCHAR(16) NOT NULL,     -- opening / active / closed / failed
    client_ip      VARCHAR(64),
    started_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    ended_at       TIMESTAMPTZ,
    bytes_in       BIGINT NOT NULL DEFAULT 0,   -- 用户按键字节数
    bytes_out      BIGINT NOT NULL DEFAULT 0,   -- 容器输出字节数
    exit_code      INT,
    error          TEXT,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at     TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX IF NOT EXISTS idx_ops_terminal_session_conn
    ON {schema}.ops_terminal_session(connection_id, started_at DESC);
CREATE INDEX IF NOT EXISTS idx_ops_terminal_session_user
    ON {schema}.ops_terminal_session(user_id, started_at DESC);
```

迁移位置：`crates/database/src/sql/ops_module_migration.sql`（`{schema}` 占位、`IF NOT EXISTS`、`COMMENT ON`，
风格对齐采集方案 §3.2），并挂到 `migrate_tenant_ops_tables` / `migrate_all_tenant_ops_tables`。

**审计纪律**：只记元数据（谁、何时、哪台连接、哪个容器、用了哪个 shell、收发字节数、退出码），
**绝不记录按键内容、不记录终端输出正文**（终端里可能出现密码、Token）。

### 2.3 与 `ops_audit_log` 的关系

总方案 §7 规划的 `ops_audit_log`（append-only、DB 侧禁 UPDATE/DELETE）是 V1.2 的通用高危操作审计表。
本方案的 `ops_terminal_session` 是**会话级**记录（有生命周期，需要 `ended_at` / 退出码），两者不是替代关系：

- 短期：会话表承载“谁开了终端”的审计需求；
- V1.2：在 `open/close` 两个动作上**双写**一条 `ops_audit_log`（action=`terminal.exec.open|close`），会话表继续保留用于排障。

## 3. 后端分层设计

### 3.1 `ops` crate（日志 + 性能，S1）

| 改动 | 内容 |
|---|---|
| `Cargo.toml` | `docker` feature 追加 `dep:futures`（仓库根已有 `futures = "0.3.34"`，`ops` 目前未用）；用途是 `StreamExt::next` |
| 新增 `src/probe.rs` | `ContainerLogsRequest` / `ContainerLogLine` / `ContainerLogs` / `ContainerStats` + 三个纯函数；`lib.rs` re-export |
| `connector/docker.rs` | 新增 `DockerConnector::container_logs` / `container_stats` 两个方法（复用既有 `map_request_error`） |
| `README.md` + `lib.rs` 文档头 | 只读清单补两条 GET：`/containers/{id}/logs`、`/containers/{id}/stats`，并注明“不 exec” |

对外类型（`serde::Serialize`；本结构没有 i64 ID 字段，不涉及大整数转字符串约定）：

```rust
pub struct ContainerLogsRequest {
    pub lines: Option<u32>,       // 默认 200，夹到 1..=2000（对齐总方案 §4「200~500 行」）
    pub timestamps: bool,
    pub max_bytes: Option<usize>, // 默认 512 KiB
}
```

### 3.8 `ops-exec` 的 K8s backend（K2）

Cargo 只需在 `ops-exec` 内局部追加 `ws`，不改根 workspace 里 kube 的 features 列表：

```toml
kube = {workspace = true, features = ["ws"]}
```

实现骨架：

```rust
let api: Api<Pod> = Api::namespaced(client, namespace);
let attach = AttachParams::interactive_tty()   // stdin/stdout on、stderr off、tty on
    .container(container);                     // 多容器 Pod 必填
let mut process = api.exec(pod, shell_cmd, &attach).await?;  // shell_cmd 形如 vec!["/bin/sh"]

let mut stdin = process.stdin().ok_or(ExecError::NoStdin)?;
let mut stdout = process.stdout().ok_or(ExecError::NoStdout)?;
let mut resize = process.terminal_size().ok_or(ExecError::NoTty)?;
resize.send(TerminalSize { width: cols, height: rows }).await?;
```

- **读干再 `join()`**：`process.join().await` 必须在 stdout EOF 之后调用（§1.5 坑 3），否则死锁；
- 退出码：先 `take_status()` 拿 `Status`，从 `details.causes` 中找 `reason == "ExitCode"` 的 `message` 解析为 `i32`；
  拿不到时按 `status == "Success" ? 0 : 1` 兜底，再拿不到返回 `None`；
- **无 shell 识别**：错误信息含 `executable file not found` / `no such file or directory` → `ExecError::NoShell`；
  也可先用白名单探测（与 Docker 侧同一顺序：`/bin/sh` → `/bin/bash` → `/bin/ash` → `/busybox/sh`）；
- 会话断开：WS 关闭即 drop `AttachedProcess`（其 `Drop` 会 abort 后台任务）；K8s exec 会话**不可重连**，需重新打开。

终端会话的 `target` 描述符（Docker 与 K8s 共用同一套会话/WS/前端，只有 backend 不同）：

```json
{ "connectionId": "123", "target": { "kind": "docker", "container": "otel-collector" },
  "shell": "/bin/sh", "cols": 120, "rows": 32 }
```

```json
{ "connectionId": "456", "target": { "kind": "k8s", "namespace": "prod", "pod": "web-0", "container": "web" },
  "shell": "/bin/sh", "cols": 120, "rows": 32 }
```

> 日志 / 指标**不强行统一**路径：Docker 用 `containers/{containerId}`，K8s 必须带 `namespaces/{ns}/pods/{pod}`
> （多容器 Pod 还要 `container` 查询参数）。统一只会得到一堆 `Option`，反而容易漏校验。

WS 帧协议（与 `ssh_routes.rs` 完全一致，前端可复用同一套解析）：

| 方向 | 帧类型 | 内容 | 语义 |
|---|---|---|---|
| 客户端 → 服务端 | Binary | 原始字节 | 按键 / 粘贴，直接 `write_input` |
| 客户端 → 服务端 | Text | `{"type":"resize","cols":120,"rows":32}` | 调用 `resize_session`（仅 tty 生效） |
| 客户端 → 服务端 | Text | `{"type":"ping"}` / `{"type":"close"}` | 保活 / 主动断开 |
| 服务端 → 客户端 | Binary | 终端输出字节 | 直接 `term.write`，保留 ANSI |
| 服务端 → 客户端 | Text | `{"type":"exit","code":0}` | 进程退出（Docker `inspect_exec` / K8s `take_status`） |
| 服务端 → 客户端 | Text | `{"type":"closed","reason":"…"}` | 会话关闭原因 |
| 服务端 → 客户端 | Text | `{"type":"pong"}` | 保活应答 |

`httpAdapter.extractParams()` 的既有规则（见采集方案 §4）：路径占位符从入参拼 URL，GET 剩余参数进 query，
非 GET 剩余参数进 JSON body —— 因此 `get_ops_container_logs({ connectionId, container, lines })` 会自然拆成
`path + ?lines=…`，`open_ops_terminal_session({...})` 会整体进 body，无需特判。

## 5. 安全与合规

### 5.1 前提事实（决定了必须做连接分级）

总方案 §6.1 已经写明：**Docker API 没有细粒度权限**，能连 socket 就能做任何事。因此“只读采集”与“容器终端”
必须落在**不同连接配置**上：

| 连接用途 | 允许的能力 | 凭证/端点建议 |
|---|---|---|
| 发现采集（`ops`） | ping / version / list_* / logs / stats / top_processes | 只读账号或受限代理；优先本机 socket 或 mTLS |
| 受控终端（`ops-exec`） | 上面的全部 + exec | 单独一条连接，仅授权运维管理员；**禁止** `plain_tcp`（2375 明文） |

实现上：`ops_connection` 增加 `exec_enabled SMALLINT NOT NULL DEFAULT 0`，`open_session` 必须校验该列为 1。

### 5.2 三重开关（默认全关）

1. **环境开关**：`OPS_CONTAINER_EXEC_ENABLED=false`（缺省关闭；关闭时 `open_session` 直接返回 400「未启用容器终端」）；
2. **连接开关**：`ops_connection.exec_enabled`（默认 0，界面上默认不勾选）；
3. **权限点**：`ops:terminal:exec`（只授运维管理员角色，普通只读角色不授）。

任一层不满足即拒绝，且拒绝原因要能区分（前端提示不同文案，避免“不知道为什么打不开”）。

### 5.3 审计

- 落 `ops_terminal_session`（`opening → active → closed / failed`），字段见 §2.2；
- 只记元数据：`provider` / `target_kind` / `connection_id` / `container_uid` / `namespace` / `pod_name` /
  `container_name` / `shell` / `user_id` / `client_ip` / 收发字节 / 退出码 / 时长；
- **不记**按键内容、**不记**终端输出（可能含密码、Token、连接串）；
- 断开双触发要幂等：WS 关闭与前端 `DELETE` 都会调 `close_session`，实现与 `ssh_service::close_session` 一样做成重复调用安全；
- V1.2 起在 open/close 上双写 `ops_audit_log`（append-only）。

### 5.4 内容与配额限制

| 项 | 取值 | 说明 |
|---|---|---|
| 日志行数 | 默认 200，上限 2000 | 对齐总方案 §4「200~500 行」；`tail` 直接透传给 daemon |
| 日志字节 | 默认 512 KiB | 超出置 `truncated=true` 并停止读取，drop 流即断开 |
| 指标采样 | `twoSamples` 最多 2 条样本 | Docker 约 1s 一条，单次请求最多占 2s；超时按连接超时兜底 |
| 终端并发 | 每用户 3 个会话 | 复用 `DEFAULT_MAX_SESSIONS_PER_USER` 口径（`SSH_MAX_SESSIONS_PER_USER` 可覆盖） |
| 终端空闲 | 1800s 回收 | 复用 `DEFAULT_IDLE_SECS` 口径（`SSH_SESSION_IDLE_SECS` 可覆盖） |
| 终端单次输入 | 32 KiB/帧 | 超过则拒绝该帧，避免前端一次粘贴灌爆后端 |

### 5.5 脱敏与可观测

- 日志正文在**返回前**执行脱敏（正则清单沿用总方案 §4.3：Bearer Token、私钥块、`password=`、连接串），
  替换为 `***`；脱敏在 service 层做，前端不做二次处理；
- `tracing` 只记录元数据（`connection_id` / `container_id` / 行数 / 字节数 / 耗时 / 退出码），
  **不得**把日志正文或终端输出写进日志；
- 终端会话建立与关闭各打一条 `info`，`session_id` 作为 span 字段，便于与 `ops_terminal_session` 对齐。

## 6. 关键实现细节与坑

### 6.1 CPU% 有两条路径，`one-shot` 通常算不出来

- 公式：`cpu_delta = total_usage - prev_total_usage`，`system_delta = system_cpu_usage - prev_system_cpu_usage`，
  `cpu_percent = cpu_delta / system_delta * online_cpus * 100`（多核可 > 100）。
- `one_shot=true` 时 `precpu_stats` 往往为空、`preread` 可能被省略或为 `0001-01-01`，`system_delta <= 0` ⇒ 返回 `None`；
  前端此时显示「采样中」或直接展示绝对值（内存 / 网络 / pids 仍可用）。
- 需要准确曲线时用 `.stream(true)` 取**前两条样本**（Docker 约 1s 一条）自己算 delta，取完立即 drop 流。
- 重启后的第一帧 `total_usage` 会回退，`cpu_delta < 0` 必须判掉，否则会算出负数。

### 6.2 内存工作集必须减掉页缓存

`memory_stats.usage` 含 page cache，直接除以 `limit` 会虚高（Java/Go 服务尤其明显）。与 `docker stats` 一致的做法：

```text
used = usage - mem_cache_bytes
mem_cache_bytes = stats["total_inactive_file"]   // cgroup v1
               ?? stats["inactive_file"]         // cgroup v2
               ?? stats["cache"]                 // 兜底
               ?? 0
```

`limit` 在未限制内存时是宿主总内存量级，`mem_percent` 仅供参考，界面需同时显示绝对值。

### 6.3 网络与块设备

- 网络：`networks` 是多网卡 map，`rx_bytes` / `tx_bytes` 要**求和**；容器无网络时字段整体缺失（返回 0/0）。
- 块设备：`blkio_stats.io_service_bytes_recursive` 里按 `op`（`Read` / `Write`）求和；
  **cgroup v2 下部分字段为 null**（`io_serviced_recursive` 等仅 v1 有），所以 `blkio_*` 用 `Option`。
- Windows 容器：`storage_stats` / `num_procs` 才有意义，`cpu_stats.online_cpus` 为 0；不特殊处理也能返回，但前端不要按 Linux 语义解释。

### 6.4 日志接口的三个细节

| 细节 | 事实 | 处理方式 |
|---|---|---|
| `tail` 是 `&str` | `LogsOptionsBuilder::tail(&str)`，取值 `"200"` 或 `"all"` | 先把 `u32` 夹到 1..=2000 再 `to_string()` |
| 日志驱动不支持 | 非 `json-file` / `journald`（如 `syslog`）会返回 501 | 映射为 `OpsError::Api`，前端提示「该容器日志驱动不支持 API 读取」 |
| 停止/已退出容器 | `logs` 仍可读（这正是排查崩溃的入口） | 不要先判 running；`stats` 才需要运行中，失败按 409/500 统一提示「容器未运行」 |
| 非 UTF-8 | `LogOutput.message` 是 `Bytes` | `String::from_utf8_lossy`，不要 `from_utf8().unwrap()` |

### 6.5 终端特有的四个坑

1. **`start_exec` 是 HTTP Upgrade**：`exec.rs:253-267` 带 `Connection: Upgrade` / `Upgrade: tcp`；
   反向代理（nginx）必须放行，否则表现是「会话建立成功但没有任何输出」。与 SSH WS 是同一类配置问题。
2. **`tty=true` 输出只有 `Console`**：bollard 用 `NewlineLogOutputDecoder::new(true)`（`exec.rs:270`），
   `read.rs:50-69` 对 TCP 分支整块返回 `Console`；stdout/stderr 已合并，不要 demux，也不要按行重组。
3. **`output_capacity` 默认 8 KiB**：中文 + ANSI 转义下会被切得很碎，xterm 侧表现为「输出一顿一顿」；
   终端场景显式设 16~64 KiB。
4. **`resize` 只对 `tty=true` 生效**，且必须在 `create_exec` 时就把 `tty` 设成 `Some(true)`；
   事后改不了，只能重建 exec 实例。

### 6.6 连接器生命周期（mTLS 场景最容易踩）

`DockerConnector.cert_material` 是 `%TEMP%` 下 mTLS 证书目录的守卫（采集方案 §1.3）：
客户端证书由 `DockerClientCertResolver` **在每次 TLS 握手时**才从磁盘读。因此：

- `ContainerExecSession` 必须**整体持有 `DockerConnector`**，不能只 clone `Docker` 客户端后把连接器丢掉；
- 同理，`container_logs` / `container_stats` 应在同一个连接器实例上完成一次完整调用，不要“取 client → drop connector → 再请求”；
- service 层做连接缓存时，缓存键要包含连接 ID + 凭证版本，凭证更新后必须让旧连接器（及其临时目录）及时释放。

### 6.7 汇总表

| 现象 | 根因 | 规避 |
|---|---|---|
| 日志为空 | `stdout/stderr` 默认 false | builder 显式 `.stdout(true).stderr(true)` |
| 性能页一直转圈 | `StatsOptions` 默认 `stream=true` | `.stream(false).one_shot(true)` 或 `.take(2)` |
| 输出卡顿/断行 | `output_capacity` 8 KiB | 提到 16~64 KiB |
| 会话能开但无输出 | 反代未放行 Upgrade | 放行 `Connection` / `Upgrade` 头 |
| 无 shell 返回裸 500 | 未识别 OCI runtime 错误 | 映射 `ExecError::NoShell` + 中文提示 |
| mTLS 握手偶发失败 | 连接器被提前 Drop | 会话持有连接器本体 |
| 时间戳对不上 | `BollardDate` 时区 | 沿用既有 `date_millis()`（`time` feature，取 epoch 毫秒） |

### 6.8 K8s 特有的坑

| 现象 | 根因 | 规避 |
|---|---|---|
| `exec` 编译不过（找不到 `AttachParams` / `Execute`） | kube 未开 `ws` feature | `ops-exec` 内 `kube = {workspace = true, features = ["ws"]}` |
| 指标请求 404 | 用 `from_gvk` → 资源名被算成 `podmetrics` | `from_gvk_with_plural(..., "pods")` |
| 指标 404/403 但日志正常 | 集群未装 metrics-server / 账号无 `metrics.k8s.io` 权限 | 映射为中文提示 + `kubectl top pods` 自检建议 |
| 终端能开但无输出、命令卡死 | 先 `join()` 后读 stdout，内部缓冲写满 | 先读干 stdout/stderr，再 `join()`（§1.5 坑 3） |
| 终端报 TTY 相关错误或输出错乱 | 同时开 `tty=true` 与 `stderr=true`（复用协议不支持） | 用 `AttachParams::interactive_tty()`（stderr 默认 false） |
| 多容器 Pod 报 `a container name must be specified` | 未传 `container` | 从 `pod.spec.containers` 取默认首容器，或界面让用户选 |
| 日志被截断 / 行序错乱 | 一次性 `logs()` 拉大量数据 | 用 `log_stream().lines()` + `limit_bytes` + 应用层字节上限 |
| `previous=true` 报 `previous terminated container not found` | 该容器从未重启过 | 首次失败即回退为普通日志，并提示「无上次运行记录」 |
| 指标某容器为空 | `PodMetrics` 尚无该容器样本（刚创建） | 该容器返回 0 并标「暂无样本」，不要整体报错 |
| `kubectl top` 有值但接口为空 | metrics-server 聚合层 / `--kubelet-insecure-tls` 异常 | 文档给出 `kubectl get --raw /apis/metrics.k8s.io/v1beta1` 排查命令 |

> K8s 的日志是 kubelet 原样转出的行（CRI 格式），**不做 JSON 解析**，避免把 `{"log":"...","stream":"stdout"}`
> 这类内容二次包装；直接按行展示，脱敏在 service 层统一做。

| 5 | cgroup v1 / v2 差异 | 已按字段优先级处理（§6.2 / §6.3）；Windows 容器字段不同，前端按 `os_type` 分支展示 | 老集群（v1）与新集群（v2）指标口径需一致 |
| 6 | 前端公共 hook 重构范围 | `useSshTerminal` 与 `useContainerTerminal` 抽公共实现会改动既有 SSH 面板；建议先复制实现保证 S4 可用，再在 S5 收敛 | 若重构范围过大，会连带 SSH 终端回归 |
| 7 | K8s 终端依赖 `ws` feature | kube-rs 的 `Api::exec` / `AttachParams` 被 `#[cfg(feature = "ws")]` 门控，当前根 `Cargo.toml` 未开；在 `ops-exec` 内局部追加 `features = ["ws"]` 即可，不影响 `ops` | 会引入 `tokio-tungstenite`，桌面端编译时间与包体积上涨，需在 K1 前做一次构建耗时对比 |
| 8 | metrics-server 非必装 | K8s 没有内置容器指标；未装 metrics-server 时性能页只能显示「不可用 + 自检命令」 | 验收需区分「集群已装 / 未装」两种环境 |
| 9 | 指标口径不一致 | K8s 只有 CPU / 内存，无网络 / 块设备 / pids；Docker 侧字段更全 | 前端按 provider 渲染不同字段，接口不假装字段通用 |
| 10 | `ApiResource` plural | `from_gvk` 会把 `PodMetrics` 算成 `podmetrics`，必须 `from_gvk_with_plural(..., "pods")` | 写错就是 404，且很容易误判为「集群没装 metrics-server」 |
| 11 | K8s exec 不可重连 | WS 断开即回收，`AttachedProcess` 无法复用 | 前端提示「重新打开终端」，不做自动续接 |

## 附录 A 容器无 shell 时的替代路径

`scratch` / distroless 镜像（本仓的 `otel-collector` 就是）没有 shell，终端能力对它天然不可用。
以下三条路径按“侵入性从低到高”排列，前两条不改变任何镜像。

### A.1 只读手段（零侵入，首选）

| 需求 | 能力 | 说明 |
|---|---|---|
| 看日志 | `GET /containers/{id}/logs` | daemon 侧读日志驱动，不进入容器 |
| 看 CPU / 内存 / 网络 / pids | `GET /containers/{id}/stats` | daemon 侧读 cgroup |
| 看进程列表 | `docker.top_processes()` | 等价 `docker top`，返回 `Titles` + `Processes` |
| 看退出码 / 重启次数 / 健康检查 | `docker.inspect_container()` | `State.ExitCode`、`RestartCount`、`State.Health` |
| 探端口 | 共享网络命名空间的 sidecar（见 A.2） | 例如 `ss -lntp` / `curl localhost:4318` |

### A.2 调试 sidecar（不改变目标镜像）

```bash
# 与目标容器共享网络 + PID 命名空间：可看端口、可看进程、可读它的根文件系统
docker run --rm -it \
  --network container:otel-collector \
  --pid container:otel-collector \
  --volumes-from otel-collector \
  nicolaka/netshoot
```

进去后可执行 `ss -lntp`、`curl`、`tcpdump`，以及 `ls /proc/1/root` 浏览目标容器的根文件系统
（`--pid` 因权限被拒时，去掉该参数只保留 `--network` 也能完成网络层排查）。

### A.3 自建带 shell 的调试镜像（需要改部署）

`COPY --from` 从 `scratch` 镜像取二进制是合法的，因此可以在不重新编译采集器的前提下得到一个可登录的同版本镜像：

```dockerfile
FROM otel/opentelemetry-collector-contrib:latest AS otel
FROM alpine:3.20
RUN apk add --no-cache curl busybox-extras
COPY --from=otel /otelcol-contrib /otelcol-contrib
COPY --from=otel /etc/otelcol-contrib/config.yaml /etc/otelcol-contrib/config.yaml
COPY --from=otel /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/ca-certificates.crt
USER 10001:10001
ENTRYPOINT ["/otelcol-contrib"]
```

把 `docker-compose.yml` 的 `image:` 换成 `build: .`，`docker compose up -d --build` 后即可 `docker exec -it otel-collector sh`。
**仅限排障环境**，生产不建议替换官方镜像（失去签名与升级路径）。

### A.4 与“真终端”的取舍

| 方案 | 是否需要 shell | 是否改变镜像 | 适合场景 |
|---|---|---|---|
| A.1 只读接口 | 否 | 否 | 日常排障、告警定位（本方案 S1 交付） |
| A.2 sidecar | 否（用 sidecar 的 shell） | 否 | 临时深度排查、抓包、看进程 |
| A.3 调试镜像 | 是 | **是** | 需要长期在容器内操作，且能接受自建镜像 |
| 本方案终端（exec） | **是** | 否 | 业务容器（alpine/debian/nginx）的常规运维 |

## 附录 B 代码骨架

### B.1 日志（`ops::connector::docker::DockerConnector`）

```rust
pub async fn container_logs(
    &self,
    container: &str,
    request: &ContainerLogsRequest,
) -> OpsResult<ContainerLogs> {
    let tail = request.lines.unwrap_or(200).clamp(1, 2000).to_string();
    let options = LogsOptionsBuilder::new()
        .stdout(true)            // 默认 false，必须显式开
        .stderr(true)
        .timestamps(request.timestamps)
        .tail(&tail)             // 注意是 &str
        .follow(false)           // 本轮不做实时流
        .build();

    let mut stream = self.docker.logs(container, Some(options));
    let max_bytes = request.max_bytes.unwrap_or(512 * 1024);
    let mut lines = Vec::new();
    let mut bytes = 0usize;
    let mut truncated = false;

    while let Some(item) = stream.next().await {
        let item = item.map_err(|err| map_request_error("GET /containers/{id}/logs", err))?;
        let (stream_name, message) = match item {
            LogOutput::StdOut { message } => ("stdout", message),
            LogOutput::StdErr { message } => ("stderr", message),
            LogOutput::StdIn { message } => ("stdin", message),
            LogOutput::Console { message } => ("console", message),
        };
        bytes += message.len();
        if bytes > max_bytes {
            truncated = true;
            break;                    // drop(stream) 即断开，不挂连接
        }
        lines.push(ContainerLogLine {
            stream: stream_name,
            message: String::from_utf8_lossy(&message).into_owned(),
        });
    }

    Ok(ContainerLogs { container: container.to_string(), lines, bytes, truncated })
}
```

### B.2 性能（两种采样模式）

```rust
pub async fn container_stats(
    &self,
    container: &str,
    two_samples: bool,
) -> OpsResult<ContainerStats> {
    if two_samples {
        // stream=true 时约 1s 一条；取两条自己算 delta，CPU% 才准
        let options = StatsOptionsBuilder::new().stream(true).build();
        let mut stream = self.docker.stats(container, Some(options));
        let first = next_sample(&mut stream).await?;
        let second = next_sample(&mut stream).await?;
        Ok(ContainerStats::from_samples(&second, Some(&first)))
    } else {
        // 默认 stream=true，必须显式关掉，否则永远不结束
        let options = StatsOptionsBuilder::new().stream(false).one_shot(true).build();
        let mut stream = self.docker.stats(container, Some(options));
        let sample = next_sample(&mut stream).await?;
        Ok(ContainerStats::from_samples(&sample, None))
    }
}

async fn next_sample<S>(stream: &mut S) -> OpsResult<ContainerStatsResponse>
where
    S: futures::Stream<Item = Result<ContainerStatsResponse, bollard::errors::Error>> + Unpin,
{
    stream
        .next()
        .await
        .ok_or_else(|| OpsError::Api("GET /containers/{id}/stats 未返回样本".into()))?
        .map_err(|err| map_request_error("GET /containers/{id}/stats", err))
}
```

`map_exec_error` 需要把“无 shell”单独识别出来：

```rust
fn map_exec_error(err: bollard::errors::Error, shell: &str) -> ExecError {
    let text = err.to_string();
    if text.contains("executable file not found") || text.contains("no such file or directory") {
        ExecError::NoShell(shell.to_string())
    } else {
        ExecError::Docker(text)
    }
}
```

界面文案（`ExecError::NoShell`）：

> 该镜像不含 shell（scratch / distroless），无法打开终端。可改用「日志 / 性能」面板，
> 或按本文档附录 A 使用 debug sidecar。
