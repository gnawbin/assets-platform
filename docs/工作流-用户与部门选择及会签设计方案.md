## 1. 背景与目标

在审批流、任务流转中，「选择用户」和「部门选项」是核心配置能力。当前工作流编辑器中的「人工审批」节点只能手填审批人字符串，存在以下问题：

1. 用户不知道应该填用户 ID、用户名还是部门名称；
2. 保存后再次打开节点时无法显示审批人姓名；
3. 无法按部门负责人、部门成员自动分配；
4. 无法绑定流程表单中的用户字段；
5. 不支持多用户会签 / 或签；
6. 待办列表没有按当前用户过滤，也没有显示审批人姓名。

本方案的目标：

- 在流程设计器中提供「左树右表」的选人交互；
- 支持指定用户、指定部门、表单字段三种审批人来源；
- 支持单人、会签（全部通过）、或签（任一通过）；
- 支持数据回显、审批意见聚合、待办权限过滤；
- 不 fork 外部 `engine-core`，不破坏现有单人审批流程。

### 2.2 现有选人组件

| 组件 | 现状 | 问题 |
| --- | --- | --- |
| `DepartmentUserSelect.tsx` | 左侧部门 Radio 平铺列表，右侧用户 Select 下拉 | 不是左树右表；无部门搜索；不适合流程配置 |
| `DepartmentTreeSelector.tsx` | 部门多选弹窗，内部有树构建、搜索、子部门计算 | 仅用于部门选择，没有用户列表联动 |

### 2.3 关键缺口

1. **审批节点没有选人入口**：`EngineFieldsPanel` 中审批人是自由文本。
2. **没有姓名回显**：只保存 ID，重新打开节点只能看到雪花 ID。
3. **没有部门负责人字段**：`public.sys_department` 没有 `leader_id`。
4. **后端只支持单个 assignee**：`engine-core` 的 `BpmnElement::UserTask(String)` 只有一个字符串。
5. **待办没有用户过滤**：`list_pending_tasks` 返回全部任务，前端直接展示 `task.assignee`。
6. **工作流 HTTP 通道缺失**：前端 `workflowService.ts` 全部走 HTTP，但 `crates/api` 没有工作流路由，`httpAdapter.ts` 也没有命令映射；这些命令目前只注册在 Tauri `invoke_handler` 中。

> 第 6 条是当前工作流功能在 Web / 桌面纯 HTTP 模式下无法调用的阻塞项，必须作为 Phase 0 处理。

### 2.4 外部引擎能力核对

`engine-core` 是 `bpmninja` 的固定 git 依赖（rev `74a0d0ee865af4215255d9fed5ce61a0c5a2bcbb`），其用户任务定义：

```rust
pub enum BpmnElement {
    // ...
    /// A user task assigned to a specific role or user.
    UserTask(String),
    // ...
}
```

结论：

- 原生 **不支持 UserTask 多实例**；
- 支持 `ParallelGateway`、`ExclusiveGateway`、`TerminateEndEvent`；
- `TerminateEndEvent` 会清理该实例所有待办；
- 条件表达式支持 `&&`、`||`、比较、变量路径等；
- 因此可以通过「一个 UserTask + 后端审批组投票聚合」实现会签/或签，无需修改引擎。

## 3. 总体设计

### 3.1 设计原则

1. **保持标准 BPMN**：画布只使用标准 `bpmn:UserTask`，不新增私有节点类型。
2. **扩展参数放 `assets:EngineConfig`**：审批方式、部门、表单字段、会签类型等写入 BPMN 标准扩展点。
3. **引擎侧单任务**：会签/或签在引擎中仍是一个 UserTask，assignee 写 `group:<nodeId>` 令牌。
4. **后端聚合投票**：候选人、投票、终态判断由后端负责。
5. **执行级快照**：审批组成员在流程启动时解析并写入 `__workflow` 快照，不按执行实例重新部署流程定义。
6. **向后兼容**：只有 `assignee` 的旧流程继续走单人审批路径。

### 3.2 总体架构

```text
┌──────────────────────────────┐

               │

│  - 用户 / 部门 / 表单字段     │

│  - 写入 __workflow 快照       │
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│ engine-core                   │
│  一个 PendingUserTask         │
│  assignee = group:<nodeId>    │
└──────────────┬───────────────┘

│  approved=true/false          │
└──────────────────────────────┘
```

### 3.3 关键决策

| 决策 | 说明 |
| --- | --- |
| 不 fork `engine-core` | 外部依赖维护成本高；用审批组聚合满足会签/或签 |
| 不按执行实例重新部署定义 | 动态审批人只影响执行快照与审批组，不造成定义版本膨胀 |
| group token | 引擎 assignee 写 `group:<nodeId>`，后端识别并展开为成员待办 |
| 拒绝分支静态展开 | `UserTask -> DecisionGateway -> 原目标 / TerminateEndEvent` |
| 会签/或签统一模型 | 两种类型共用审批组、投票表、终态判断 |
| 表单字段只绑定变量 | 当前没有工作流表单设计器，绑定的是 `inputData` / 流程变量 |

## 5. 部门负责人 / 部门成员

### 5.1 数据库变更

部门表位于 `public` schema：

```sql
-- public_tables.sql：新建库直接包含该列
CREATE TABLE IF NOT EXISTS public.sys_department (
    id BIGINT PRIMARY KEY,
    tenant_id BIGINT NOT NULL REFERENCES public.sys_tenant (id),
    department_name VARCHAR(255) NOT NULL,
    parent_id BIGINT,
    leader_id BIGINT,
    description TEXT,
    -- ...

-- public_migration.sql：已有库幂等补列
ALTER TABLE public.sys_department
ADD COLUMN IF NOT EXISTS leader_id BIGINT;
```

说明：

- `leader_id` 允许为空，历史部门需要管理员补录；
- 不新增外键，避免删除用户时阻塞部门维护；
- 查询时校验用户存在、未删除、状态启用、租户一致。

```text
   - status != 0

```

部门成员规则：

```sql
SELECT id, real_name, username
FROM public.sys_user
WHERE department_id = $1
  AND tenant_id = $2
  AND (deleted IS NULL OR deleted = 0)
  AND status <> 0
ORDER BY id ASC;
```

可选包含子部门：

```text
先递归收集 department_id + 所有后代部门 ID
再使用 department_id = ANY($1)
```

## 6. 表单字段绑定

### 6.1 配置语义

`assigneeMode = "form"` 时，使用 `assigneeFormField` 指定变量路径：

```text
approver_id
form.approver_id
form.approver_ids
```

支持：

- 顶层字段；
- 点路径；
- 数组下标（如 `form.approvers[0].id`，可选）；
- 字符串数组 / 数字字符串数组。

### 6.2 值解析规则

| 表单值 | 解析结果 |
| --- | --- |
| `"1234567890"` | 单人 |
| `1234567890` | 单人（转字符串） |
| `["123", "456"]` | 多人 |
| `[{"user_id": "123"}]` | 多人（读取 `user_id` / `id`） |
| `""` / `null` / `[]` | 执行前报错 |
| 不存在的用户 | 执行前报错 |
| 禁用 / 删除用户 | 执行前报错 |

### 6.3 解析时机

在 `execute_workflow` 启动实例之前解析：

```text
1. 合并 input_data 到 variables
2. 遍历 IR 中的审批节点
3. 对 assigneeMode=form 的节点：
   - 读取 variables 中的路径
   - 校验并去重用户
   - 生成 ApprovalGroupPlan
4. 任意节点解析失败 → 整个执行失败，不创建实例
```

### 6.4 执行快照

把解析结果写入 `__workflow` 变量：

```json
{
```

## 7. 审批组与会签 / 或签

### 7.1 引擎侧：group token

`BpmnCompiler::compile` 根据 IR 配置决定 UserTask 的 assignee：

```text
approval_type = all / any
或 assignee_mode = department / form
或 assignee_ids 数量 > 1
    → UserTask("group:<nodeId>")

否则
    → UserTask(assignee)
```

示例：

```xml
<bpmn:userTask id="Approve_1" name="人工审批" data-assignee="group:Approve_1" />
```

引擎只看到一个待办：

```text
PendingUserTask {
  task_id: ...,
  node_id: "Approve_1",
  assignee: "group:Approve_1"
}
```

后端识别 `group:` 前缀后，不再把它当成真实用户，而是展开为审批组。

### 7.4 终态规则

| 类型 | 通过条件 | 拒绝条件 |
| --- | --- | --- |
| `single` | 该审批人通过 | 该审批人拒绝 |
| `all`（会签） | 全部成员通过 | 任一成员拒绝 → 立即拒绝 |
| `any`（或签） | 任一成员通过 → 立即通过 | 全部成员拒绝 → 拒绝 |

> 或签采用“任一通过即通过；全部拒绝才拒绝”。任一拒绝不会立即终止，需要等待其他成员是否通过。

状态机：

```text
open
 ├─ all: 全部通过        -> approved
 ├─ any: 任一通过        -> approved
 └─ all: 任一拒绝 / any: 全部拒绝 -> rejected
```

### 7.5 并发与幂等

同一审批组可能被多个用户同时提交，必须保证：

1. `workflow_approval_vote(engine_task_id, user_id)` 唯一索引防重复投票；
2. 终态判断在数据库事务中执行：

```sql
SELECT *
FROM {schema}.workflow_approval_group
WHERE engine_task_id = $1
FOR UPDATE;
```

3. 只有 group 状态为 `open` 才允许投票；
4. 终态更新与 `engine.complete_user_task` 调用顺序：
   - 先锁 group；
   - 插入 vote；
   - 计算终态；
   - 更新 group 状态；
   - 提交事务；
   - 调用引擎完成任务；
   - 记录节点结果。
5. 如果引擎完成失败：
   - group 状态回滚为 `open`，或记录 `finalize_error`；
   - 允许重试；
   - 不能留下“group 已通过但引擎任务仍挂起”的不一致状态。

### 7.6 拒绝分支展开

对 `reject_action = terminate` 的审批节点，`BpmnCompiler` 在解析后做静态展开：

```text
原：
Incoming -> UserTask(Approve_1) -> Outgoing

展开：
Incoming -> UserTask(Approve_1) -> DecisionGateway
                                      ├─ approved == true && <原条件> -> 原目标
                                      └─ approved == false -> TerminateEndEvent
```

要点：

- **保留原 UserTask 节点**，边界事件仍附加在原节点上；
- 原出线条件保留，与 `approved == true` 组合；
- `DecisionGateway` 至少 2 条出线，满足引擎校验；
- `TerminateEndEvent` 会清理该实例所有待办；
- `reject_action = continue` 时不展开，保持原有“审批后继续”的行为。

示例：

```text
UserTask Approve_1
  -> Decision_Approve_1
       -- ${approved == true && amount > 1000} --> Manager_Approve
       -- ${approved == true && amount <= 1000} --> Auto_Approve
       -- ${approved == false} --> Reject_End (TerminateEndEvent)
```

> 条件表达式使用引擎支持的 `${...}` 语法，支持 `&&`、比较、变量路径。

> 决策变量默认 `approved`。如果节点配置了 `approval_variable`（例如 `result`），审批完成时需要同时写入 `approved` 与该变量，决策网关使用 `approval_variable`。

### 7.7 审批结果聚合

同一逻辑审批节点可能有多条投票，节点结果不能按 `node_id` 覆盖。

建议结构：

```json
{
  "node_id": "Approve_1",
  "status": "success",
  "output": {
    "approved": false,
    "approvals": [
      {
        "task_id": "uuid",
        "assignee": "123",
        "assignee_name": "张三",
        "approved": true,
        "comment": "同意"
      },
      {
        "task_id": "uuid",
        "assignee": "456",
        "assignee_name": "李四",
        "approved": false,
        "comment": "预算不足"
      }
    ]
  }
}
```

实现：

- `complete_user_task` 每次投票后调用 `append_approval_result`；
- 按 `node_id` 读取已有 `node_results`，向 `output.approvals` 追加；
- 终态时写入最终 `approved`；
- 前端时间线展示每个审批人的意见。

## 13. 风险、限制与后续扩展

### 13.1 风险

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| 工作流 HTTP 路由缺失 | 功能不可用 | Phase 0 优先补齐 |
| 引擎不支持 UserTask 多实例 | 无法原生会签 | 审批组 + 投票聚合 |
| 并发投票 | 重复/越权 | 唯一索引 + `FOR UPDATE` |
| 引擎完成失败 | group 与引擎状态不一致 | 事务补偿 + 可重试 |
| 部门负责人未配置 | 执行失败 | 明确错误 + 管理员补录 |
| 部门成员快照 | 中途入离职不生效 | 启动时固化，文档说明 |
| 会签拒绝终止 | 其他分支被清理 | 符合业务预期；如需退回，后续加补偿流程 |
| 旧客户端不识别新返回 | 审批结果展示异常 | 前端同步发布；旧客户端可忽略响应体 |
| 表单字段没有表单设计器 | 只能绑定变量 | 明确边界，后续独立设计 |

### 13.2 限制

1. 审批组成员在流程启动时固化，运行中不动态追加/移除；
2. 会签拒绝默认终止整个实例，不支持“拒绝后退回发起人”；
3. 审批组不支持转办、加签、委托；后续可扩展；
4. 或签的“任一通过即通过；全部拒绝才拒绝”为固定策略，暂不做节点级策略选择；
5. 表单字段只支持用户 ID / 用户 ID 数组，不支持按角色、岗位、表达式解析；
6. 部门负责人只支持单级负责人，不支持“部门负责人 + 分管领导”多级审批链；
7. 附件、审批意见模板、审批时限不在本方案范围。

### 13.3 后续扩展

- 或签策略节点级配置（任一通过 / 首个处理决定 / 任一拒绝）；
- 转办、加签、委托；
- 审批超时自动通过/拒绝；
- 部门负责人多级审批链；
- 角色、岗位、用户组作为审批人；
- 表单设计器 + 字段绑定；
- 审批意见附件与富文本。
